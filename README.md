# VOLA

VOLA is a unified training and nutrition platform for BJJ athletes who also strength train and track nutrition — one athlete profile and calendar connecting BJJ, strength training, and nutrition, with deterministic, explainable cross-sport recommendations.

- [docs/decisions/history.md](docs/decisions/history.md) — chronological project history: what's been built, why, and what's still open. Start here if you're new to this repo.
- [docs/testing/functional-scenarios.md](docs/testing/functional-scenarios.md) — recommended functional test scenarios per feature.
- [docs/architecture/deployment.md](docs/architecture/deployment.md) — dev/staging/production environment setup.
- [docs/architecture/api-conventions.md](docs/architecture/api-conventions.md) — REST/OpenAPI conventions.
- [contracts/public.openapi.yaml](contracts/public.openapi.yaml) — the wire contract.

This repo is a pnpm + Go monorepo, built incrementally, one verified piece at a time.

## Current state

- `backend/` — Go API (`cmd/api`), stdlib `net/http`. `/v1/healthz` (public), `/v1/me`, `/v1/profile` (CRUD), `/v1/modules` (read/patch — the discipline registry merged with the caller's own toggles; **the one place a new discipline is declared** is `internal/platform/discipline`, and per-user enablement is rows in `profile_modules`, so adding one needs no migration), `/v1/flags` (read-only, server-controlled feature flags), `/v1/activities` (create/list — the unified activity envelope, idempotent create for offline sync), `/v1/exercises` + `/v1/exercises/{id}` (the 504-entry exercise catalog — now also authorable from the admin console via `/v1/admin/exercises` (GET/POST/PATCH) without a deploy, the same `source=admin` split techniques use), `/v1/techniques` + `/v1/techniques/{id}` (the 542-entry BJJ technique library — separate from exercises because a technique isn't measured and lives in a position graph. Every entry carries **what it does** (`function`: advance, reverse, escape, control, finish) alongside **where it happens** (`position`) and, for the 170 transitions where it is both knowable and useful, **where it leaves you** (`to_position` — sparse and hand-authored, so absent means *not recorded*, never *goes nowhere*), which is what makes "every way to advance from here" one query instead of three category lookups — `category` stays as the colloquial label a coach would say; seeded via `cmd/seed`, and techniques are now also authorable from the admin console via `/v1/admin/techniques` (POST/PATCH) without a deploy — see migration 000032 for how the two writers stay out of each other's way, and `cmd/exportcontent` for carrying authored content back into `techniques.json`, the file the binary embeds and seeds, so it can be reviewed as a one-entry diff and promoted through a normal deploy. The authoring spreadsheet that used to generate that file was retired in 2026-08 — see docs/decisions/content-authoring-design.md), `/v1/workouts` (+ `/{id}`, `/{id}/items` — single-discipline workout templates, owner-scoped writes. `?scope=mine|public` splits your own from the **Public Workout Plans** browse surface, which now carries 17 VOLA-authored plans seeded by `cmd/seed` — bodyweight/home, dumbbell-only, PPL and upper/lower splits, a two-day 5x5 strength block and conditioning. Ownerless + `visibility=public` + `source='seed'` is what marks a plan VOLA-authored, and both the seeder's upsert and its item-replace are scoped to `source='seed'` so a deploy can never overwrite — or empty — a workout somebody owns. `scope=shared` is still accepted as a deprecated alias, because an installed mobile build updates on the App Store's schedule rather than ours), `/v1/sessions` (+ `/{id}` — including **PATCH to rename**, the one field a client may change after the fact — `/{id}/sets`, `/{id}/finish` — performed sessions and the sets in them: reps, weight, RIR, RPE and a set type, with a server-computed volume summary so both clients agree), `/v1/themes` (+ `/{weekStart}` — one free-text theme per training week: "deload", "guard retention". **Deliberately not a second focus list** — `/v1/bjj/focus` holds the rolling, technique-level "what am I working on", and a theme stores no technique ids and no exercise ids at all, which is the restriction that keeps the two from answering the same question differently. `week_start` must be a Monday: a week starting any other day would silently overlap its neighbours, the one duplicate the primary key cannot catch. PUT rather than POST, since a week holds at most one and the caller names it. Authored on web, read-only on the phone, per the platform rule that planning is a desk activity), `/v1/plans` (+ `/{planID}` — the training plan: what the athlete **intends** to train and on which day, the third leg alongside workouts (the template) and sessions (what happened). `day` is a calendar date rather than a timestamp, because "Tuesday's session" is a claim about the athlete's own calendar and an instant would slide across a day boundary when they travel; a day holds a list rather than one entry, since two-a-days are normal here; and a plan is **never reconciled** against a session — a planned day can be trained twice, ignored, or trained with something else, so adherence is a query over both resources rather than a status this one has to keep true), `/v1/body/checkins` (+ `/{date}`, `/{date}/photo` — daily weight and weekly girths, keyed on the calendar day so a save is an upsert and a retry is not a second row; an omitted measure means *not measured* and never clears a stored one, so deleting the day is how a mistyped value goes. Photos are **private**, unlike the exercise catalog's public media: the client gets a short-lived presigned PUT and the bytes never pass through the API, and the storage key is derived from the caller rather than accepted) and `/v1/body/phases` (+ `/{id}/end` — what the athlete is trying to do, as a span with a start and an end. A span rather than a profile field because a target with no date has no rate, and a rate is the only thing that can say you are cutting too fast; at most one runs at a time, enforced by a partial unique index rather than a check that loses the race), `/v1/nutrition/entries` (+ `/{id}`, `/days`) and `/v1/nutrition/foods` (+ `/{id}`) and `/v1/nutrition/estimate` (describe a meal — or photograph it — and get an **editable draft**, never a logged entry: structured outputs against a JSON schema carrying a per-item `portion_confidence` and the `assumption` behind it, because naming a food from a photo is reliable and judging the portion is not, and a portion wrong by a factor of two is invisible where a misnamed food is obvious. Metered per athlete with **two** daily caps — 20 text, 5 photo — counted separately so the dearer path cannot exhaust the cheap one (measured: ~0.95c a photo against ~0.73c a description, since the schema and system prompt dominate both); the gate runs before the model call, and failed calls count because they cost tokens too. Photos are forwarded and discarded. Needs `ANTHROPIC_API_KEY`; without it this one route serves 503 and every other nutrition route is unaffected), `/v1/nutrition/targets` (+ `/{date}`, `/suggested` — the food log, saved foods and recipes, and the calorie/macro target. **A logged entry owns its numbers**: `source_food_id` is provenance for "log this again" and no query returning nutrition follows it, so correcting a saved food cannot silently rewrite every entry ever logged from it — the join is shorter, compiles, passes every test, and the damage is invisible because there is nothing left to compare against. Targets are keyed on (user, date) rather than a mutable current row, so a day logged in March is judged against March's target. `/suggested` derives one from the live body phase — Mifflin–St Jeor resting rate, a NEAT-only activity factor that stops at 1.45 because training is added separately, plus a 28-day trailing session average — and returns the whole arithmetic alongside the answer so the athlete can argue with it; it **refuses** rather than guessing when the resting rate would come from `energy`'s generic baseline, which runs 20–30% high and would overfeed by ~400 kcal/day invisibly. Training is never credited back to the day's budget: the target already includes it, and a moving budget makes the weekly rate unreadable. kcal is authoritative and clients must not re-derive it from the macros — real labels do not reconcile against 4/4/9), `/v1/notifications` (what is waiting for you, counted per source — **derived from the pending rows themselves**, so there is no notifications table and no read/unread state: answering is what clears a count, which is the only definition that cannot desync. Sources register a counter in `cmd/api/main.go` exactly as share copiers do. Fails rather than reporting an uncountable source as zero, because a badge reading zero says "nothing is waiting"), `/v1/shares` (+ `/inbox`, `/sent` — unanswered only, so accepted and declined look identical to the sender, `/{id}/accept` — ONE share surface for every ownable thing, not a share verb per resource: a `resource_type` names the module that knows how to duplicate its own thing, registered in `cmd/api/main.go`, so the share module imports none of them — **sequences and workouts** are registered today, and the second one cost two repository methods and a line in that map, which is the whole claim the generic design was making. A shared workout's copy takes a server-generated id and is forced private and `source='user'`, so passing on a VOLA Workout can neither publish the recipient's copy to the platform nor hand it to the next deploy's seeder. Sharing is BY COPY with snapshot semantics, which is why there is no visibility column and no ACL anywhere), `/v1/feed` (what your training partners have been doing — finished sessions belonging to the caller's ACCEPTED friends who have turned `share_training_with_friends` on. **The first athlete-to-athlete read of training data in the API**: every other session read is scoped to its owner, and sharing moves copies on an explicit send-and-accept precisely so it never has to decide who may see what. Opt-in and OFF BY DEFAULT — nobody's training becomes visible because they installed an update — and the flag is read live at query time rather than stamped onto each session, so switching it off retracts everything at once. A row is the smallest thing that makes a card: who, what, when, duration and volume, never sets, notes, RPE or exercise ids — with ONE enlargement, which took a second opt-in of its own. `share_training_details` (also off by default, and inert while the switch above it is off) adds up to five exercise or technique names with the top set or the outcome beside each, because the numbers say you trained hard and the detail says what you are working on, and somebody who competes against their training partners can reasonably want the first without the second. Read live and per owner per row, so one friend opting in never speaks for another; a BJJ row never carries a `conceded` outcome, since what was done TO you belongs on your own card and not in a friend's feed. Mobile only by product decision; there is deliberately no per-item route, since the row is the whole of what a friend may see), `/v1/sessions/{sessionID}/card` (the three numbers a finished session's share card needs and the phone cannot compute for itself: the **calorie estimate** — net rather than gross, against the athlete's own Mifflin–St Jeor resting rate rather than the inflated 3.5 ml/kg/min constant, and at the Compendium's 3.5 MET for ordinary resistance work rather than the 6.0 that produces the 400–600 kcal figures consumer apps report; the **VOLA Score** — a percentile of this session's Foster load against the athlete's own last twenty of that sport, never a rating and never a comparison with anybody else, absent below eight priors because a percentile against three is noise wearing a number; and the **exercise or technique list**, whose names the offline store does not carry. All three DERIVED on read — no card table, no score column — so editing a set changes the card rather than leaving a stale figure somebody already posted. One endpoint rather than three, because a card that pops a score in a second after the calories is worse than one that waits), `/v1/friends` (+ `/requests`, `/requests/{username}/accept`, `/{username}` — the social graph: one canonically-ordered row per pair so duplicate and crossing requests are the same 409; decline IS delete, with the re-request residual recorded rather than hidden; everything addressed by handle, ids never on the wire; one 404 for every kind of miss), `/v1/users/{username}` (exact-match handle lookup returning a `{username, display_name}` public card — a dedicated type so the private profile fields cannot leak; absent, malformed and reserved handles share one 404), `/v1/profile` (now carrying `username` — the unique claimable handle the sharing design keys on, lowercase, case-insensitively unique, reserved-word-guarded — and `unit_system` — display units only; training data is always stored in kilograms and metres), `/v1/sessions/history` (training history rolled up per calendar day in the caller's timezone, with period totals and the preceding window's totals for comparison — aggregated server-side so the working-set rule lives in one place and a total can't be under-reported from a capped listing), `/v1/records` (+ `/pinned`, `/{exerciseID}/history` — personal bests per exercise, **derived on every read** rather than stored, so correcting the set behind a record retracts it instead of leaving a lift somebody never made on the board; which kinds an exercise can hold follows from its `load_type`. `/pinned` is the shortlist the athlete chooses on web — the star reads "Show on your phone" — and `/{exerciseID}/history` is that lift's arc over time, one point per session, oldest first. The arc is a **web** surface: N6 filed it as a phone chart and it failed N5's carve-out, because the at-the-rack decision is already answered by the progression recommendation and what is left is a planning question), `/v1/sessions/suggestions` (progressive overload, and an **estimated 1RM** per exercise — Brzycki with RIR/RPE folded in, so a set stopped 3 reps short isn't read as a strength loss, plus your best estimate to date; progression: what to load today per exercise **and for how many reps** — double progression autoregulated by reported effort, so reps advance inside a goal-derived range until every working set reaches the top of it, then load moves and reps reset, and three sessions stuck at one weight trigger a deload rather than another repeat. Deterministic, and it returns the evidence alongside the recommendation), `/v1/bjj/standing` + `/v1/bjj/promotions` (+ `/{promotionID}`) (an athlete's BJJ rank, **derived** server-side from the promotion history rather than stored as a column — the highest recorded rank wins regardless of promotion order or missing dates, so there's exactly one source for "what belt am I"), `/v1/bjj/sessions/{sessionID}`, `/v1/bjj/proficiency`, `/v1/bjj/positions` (the position map — the same tag stream folded by **where** rather than by technique, because "where am I losing the round" is not a technique question: getting passed from half guard is a hundred different passes and one problem. Scored and conceded are reported side by side rather than as a ratio, and `drilled` is counted but excluded from the ordering, so a position you have only ever drilled cannot outrank one you keep getting beaten in), `/v1/bjj/accomplishments` (what the athlete has actually achieved, **derived on read** from the contest record and the tag stream and stored nowhere — so correcting a result retracts the award, and there is no write verb of any kind, because an accomplishment that can be granted stops being evidence. Seven **firsts**: landing something live, the drilled→scored funnel completing across sessions, and entering / winning a match / winning by submission / a podium / gold. Each carries whether its evidence is **measured** (a bracket, a referee) or **reported** (the athlete logged it and nobody checked) — the one list in the app that puts the two side by side, which is why it is chronological and never ranked. Belt promotions are deliberately absent: `/v1/bjj/standing` already derives that fact, and two vocabularies for one fact drift), `/v1/bjj/focus` (the 3–5 techniques being worked on) (the BJJ half of a session — kind, gi, rounds × length, session RPE, and the tag stream. A BJJ session is an ordinary `sessions` row so it stays visible to history and the cross-sport load picture; this carries what a mat session has and a barbell one does not, exactly as `/{id}/sets` does for strength. Every tag records **position context and an outcome direction** — `drilled → attempted → scored` is the technique funnel, `conceded` is the symmetric half that answers "where do I keep getting stuck"), `/v1/contests` (+ `/{contestID}` — the competitive record: what you entered, in which division, and how it went. One row is one **entry**, not one event — gi and no-gi at the same tournament are two, sharing a name and a date and nothing else — with the matches inside it carrying how each one ended (`submission`, `advantage`, `decision`…), because "lost on advantages" and "lost by armbar" are different findings and a win/loss counter cannot tell them apart. Deliberately **not** named `competition`: that word already means IBJJF rule legality in the technique library. Not BJJ-scoped either — it has to hold a powerlifting meet and a 10k, so the route takes the neutral word and a client says "tournament" where that reads better. Everything in it is externally verifiable (a bracket, a placement, a referee's decision), which makes it the strongest **measured** evidence the API carries; nothing self-rated may be added, because how it felt belongs on the session. PUT replaces an entry **and every one of its matches**, since a partial update could not say what an absent bracket means; match order is assigned by the server, because it is what makes "lost in the final" different from "lost the first match"), `/v1/curricula` (+ `/{curriculumID}`, `/{curriculumID}/enrollment` — an ordered set of things to learn, and a **roadmap** once its items carry completion criteria: times scored, times defended, distinct sessions the evidence must span, a live hit rate (25 / 8 / 12 / 0.35 by default), and — for the movement fundamentals nobody scores with — distinct sessions drilled, the one criterion practice counts toward. A curriculum can carry **phases** (named, described sections — "survive the bad places first"), and its items are either **techniques** (library pointers, optionally with criteria) or **concepts** (authored text: a principle, a graduation standard — never criteria and never counted in progress, since no evidence stream could measure one); a `track` field ("belt", "foundations") is the browse-section hint, same nullable contract as `belt`. Mastery is **derived** from the BJJ session tags on every read — there is no column that could store it and no way to mark one by hand, because a roadmap whose completions can be self-declared cannot tell an athlete anything they did not already believe; the number has to be able to disappoint them. Every threshold is measured **since the athlete enrolled**, anchored on the enrollment's `started_on`, since over all time the hit rate includes the months they could not yet do the technique — which is most of what a belt syllabus is. Sharing copies the workouts model (nullable owner, NULL = VOLA-authored; `visibility`; an ownerless row must be public), so a private curriculum the caller cannot see is a 404 rather than a 403 — a 403 confirms the id exists — while a write on one they *can* see is a 403; and deleting a curriculum other athletes are working is a 409 rather than a cascade, because their enrollment is their record and not the publisher's), `/v1/sequences` (+ `/{sequenceID}` — a **chain**: what a class actually taught, in the order it flows. Six technique tags cannot say that they connect, and the connection is the lesson — "knee cut" and "knee cut off a broken closed guard" are different things to learn. Deliberately not a curriculum, though both are ordered technique lists: a curriculum's order is *pedagogical* (learn this before that, over months) and a sequence's is *causal* (this move puts you where the next one starts), so reordering one changes advice and reordering the other produces something that does not work on the mat — which is why sequences carry no criteria, no progress and no mastery, and why `UNIQUE (sequence_id, sort_order)` exists here and not there. A step records the technique **and where it leaves you**, authored rather than derived from `to_position`: that is populated for 170 of 542 techniques, so deriving would render most chains with holes — and authoring it accumulates exactly the graph data the library lacks. `null` there means *not recorded* **or** *ends the exchange*, which the technique's own `function` already tells apart. Chains are **linear**: "…and if he defends, armbar or kimura" is two sequences sharing a prefix, not one with a branch. A repeated technique in one chain is legal, unlike curriculum items — sweep, get passed, sweep again. No `visibility` and no share verb, deliberately: sharing is being built once, generically, over every ownable thing in the app), `/v1/admin/users` + `/v1/admin/users/{userID}` (admin-only, gated by a Clerk-user-ID allowlist — user lookup and per-athlete detail, both derived from `sessions`/`session_sets` rather than from any admin-specific write path; `/v1/admin/users/{userID}/activities` remains as the legacy read path for `activities` rows written before the in-app logging form was removed; `/v1/admin/users/{userID}/bjj/standing` is the same rank derivation over a path user rather than the caller, read-only). Structured JSON logging with request-ID/W3C-trace-context correlation on every request. **Rate limited per athlete** (`internal/platform/ratelimit`, token bucket) — attached to `RequireAuth` rather than to routes, so an authenticated endpoint cannot be added without a budget; keyed on the account rather than the IP, because a gym's wifi is one address; 429 carries `Retry-After` rounded up so obeying it exactly succeeds. In-memory and therefore per-instance, which is exact on today's single service and approximate the moment there are two. Real Postgres via `golang-migrate` migrations (`backend/migrations/`), both locally (`docker-compose.yml`) and on a real Railway `staging` Postgres.

#### Observability

`GET /v1/admin/health` returns recent operational problems with a summary, and
`POST /v1/client-errors` lets a client report a failure the server cannot see —
a push it has given up retrying, which would otherwise leave training on the
device while every server metric stayed green. The admin console reads them at
`/health`.

Only notable events are stored (5xx and requests slower than `SLOW_REQUEST_MS`,
default 2000) — never every request. On a healthy system the table stays close
to empty, and that emptiness is the signal.

## Run it locally

```bash
docker compose up -d              # local Postgres on :5432
cd backend && go run ./cmd/migrate up
cd backend && go run ./cmd/seed   # reference content (exercises, techniques, curricula, public workout plans); idempotent

pnpm run dev:api                  # backend API on :8080
pnpm run dev:web                  # web app on :3000
pnpm run dev:mobile               # Expo — Metro on :8081 for the development build
pnpm --filter admin dev --port 3001   # admin console on :3001 (needs its own port — apps/web also defaults to :3000)
```

**`ANTHROPIC_API_KEY` in `backend/.env` is optional.** It powers one route —
`POST /v1/nutrition/estimate`, the describe-or-photograph meal draft. Without
it that route serves 503 and everything else runs normally, so you only need a
key if you are working on that feature.

**The mobile app runs on a development build, not Expo Go.** The first run on a
machine — and any run after a new native dependency lands — has to compile and
install the app; `dev:mobile` only starts Metro and cannot deliver native code:

```bash
xcrun simctl boot <udid>          # or open Simulator.app
pnpm --dir apps/mobile run ios    # builds, installs and launches; ~10 min cold, seconds after
```

Once it is installed, `pnpm run dev:mobile` is the daily loop. `apps/mobile/ios`
and `apps/mobile/android` are generated (CNG) and gitignored — `app.json` plus
the dependency list is the source of truth, and `pnpm --dir apps/mobile run
prebuild` regenerates them from scratch.

Then open http://localhost:3000 (web) or http://localhost:3001 (admin). Each app needs its own `.env.local` (copy from `.env.example`) — the admin console additionally needs `ADMIN_USER_IDS` set to your Clerk user ID, matching the same var in `backend/.env`, before `/users` will let you in (find your ID via `GET /v1/me` or the Clerk dashboard).

### Run the backend tests

The Postgres integration tests **skip silently** unless `TEST_DATABASE_URL` is set, so `go test ./...` can look green while testing almost nothing. Give them their own database:

```bash
docker compose exec postgres createdb -U vola vola_test
cd backend && DATABASE_URL='postgres://vola:vola_dev_only@localhost:5432/vola_test?sslmode=disable' go run ./cmd/migrate up
```

Then set `TEST_DATABASE_URL` in `backend/.env` (see `backend/.env.example`) and run `pnpm run test:api`. Expect `PASS`, not `SKIP`.

### Run the checks

One command, before every push:

```bash
pnpm run verify
```

It chains every check with `&&` deliberately — run as separate lines, a failing typecheck scrolls past and the commit happens anyway. It covers the palette and icon guards, Python syntax, gofmt/vet/build, the OpenAPI spec, and lint/typecheck/test for mobile, web and admin. Everything is stdlib or already-installed tooling, so there is nothing extra to set up.

Deliberately **not** in it — each is slow or needs setup, and CI runs them:

```bash
pnpm run test:api                            # needs TEST_DATABASE_URL (see above)
pnpm run build:web && pnpm run build:admin   # slow
docker build -f backend/Dockerfile backend   # needs Docker/Colima
```

### Score a model on the dictation corpus

`evals/bjj-dictation/` pairs 33 dictated sentences with the draft a correct
extraction returns. The validator (`pnpm run check:evals`) runs in `verify` and
costs nothing; the runner makes real API calls and is never wired into a check.

```bash
python3 evals/bjj-dictation/run.py --dry-run              # build the prompt, call nothing
python3 evals/bjj-dictation/run.py --model gpt-5.6-luna   # ~33 live calls, spends money
```

It reads `OPENAI_API_KEY` from `backend/.env` (and finds the primary checkout's
copy when you are in a worktree, which never has one). Results land in
`evals/bjj-dictation/results/`; the README there carries the current scores and
what they are and are not evidence of.
